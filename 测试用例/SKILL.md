## 一级分类（按"测试维度"划分，非固定枚举，按实际业务裁剪/扩展）
一级模块是**测试维度**，不是具体业务/端。一级模块内部再按业务/端拆**二级分组**（用 `G()` 分组节点承载，不单独占一个彩虹色，仍在同一个一级模块的彩虹底色下）。

- **一级模块（维度）**：
  - **功能逻辑**：几乎所有项目都有。承载所有具体业务/端的功能测试——下单、审批、报名等任意业务功能，从接口入参校验到最终数据落库的完整过程
  - **风控**：业务涉及资金操作、账户安全、防作弊时启用。与具体业务领域无关的通用防护机制
  - **数据库**：几乎所有项目都有。技术文档所有涉及表的字段、索引、约束、业务逻辑汇总
  - **Apollo**：有该配置中心时启用
  - **Job**：有定时任务时启用
- **二级分组（挂在"功能逻辑"这个一级模块下面，按业务/端拆分，非固定枚举）**：
  - 常见分组：**现货、合约、管理后台、Web端、H5** ——按项目实际涉及的业务/端选用，不是每个项目都要凑齐
  - **策略型分组**（搬砖套利、期现套利、资金对冲、闪兑等）：这类分组内部会**编排调用**现货和/或合约的下单能力，与现货/合约平行挂在"功能逻辑"下，不要因为它们"用到了现货/合约"就把用例塞进现货或合约分组里——策略是独立的业务功能，有自己的编排逻辑（价差计算、多腿协调、超时/失败补偿等），值得单独成组
  - 每个二级分组内部再按功能点继续分（如"合约"下面还可以分"开仓""强平"等三级分组），层级不限，以清晰易读为准
  - **合约**分组特有的判断标准：只放现货没有的机制——杠杆倍数校验、保证金计算、持仓限额、维持保证金率、强制平仓、穿仓、自动减仓（ADL）等。是否该独立成"合约"分组而不是揉进"现货"分组：取决于该子领域是否有自己独立的一套状态/规则/边界条件，且只在特定场景下才存在
  - 某类规则若与具体业务/端无关、可能出现在多个不同分组里（如额度限制、异常行为检测既可能出现在下单也可能出现在提现），不要塞进"功能逻辑"下的某个二级分组，应归入独立的一级模块"风控"

### 避免模块/分组间重复覆盖
- 生成完所有内容后，检查是否有两处在断言同一件事。常见重复模式：
  - "功能逻辑-现货"分组里测了下单本身的入参校验，"功能逻辑-合约"分组又把同一个下单接口重新测了一遍入参校验——**合约分组只测合约特有的追加逻辑（杠杆/保证金部分），下单接口本身的通用校验只在"现货"分组出现一次**
  - **策略型分组（搬砖/期现/对冲/闪兑）只测策略自身的编排逻辑，不重新测它内部调用的下单/持仓接口本身**：比如"搬砖套利"分组测的是"双边价差计算是否正确""一腿成交另一腿失败时是否正确补偿/回滚""延迟导致报价过期是否正确丢弃"这类策略特有行为；而"用现货账户余额不足下单会被拒绝"这种下单本身的校验，只在"现货"分组出现一次，策略分组里可以在前置条件里直接假定"下单接口已具备该能力"，不用重新验证
  - 测试是"从接口到链路一次性执行到底"，还是"接口测试和集成测试分两个阶段/两批人做"？前者每条 TC 一次测到底（默认做法）；只有团队确实分阶段测试时，才在"功能逻辑"内部再细分"接口层"（到接口返回为止）和"链路层"（默认接口已合法，只测链路）两个三级分组，避免同一断言两处出现
  - 两处都用判定表法测了条件组合，且条件本质相同（只是换了业务场景的壳）——说明该合并统一验证，不要分散测两遍

## 用例设计方法（确定"要写哪些场景"，先于节点排版）
生成用例前，先用以下方法系统性地推导场景清单，而不是仅把文档里出现的场景直接照抄——文档描述的通常只是正向主流程，遗漏的边界/组合/异常场景要靠方法论补出来。

- **等价类划分**：每个输入/条件先划分为有效等价类与无效等价类，每类至少各取一个代表值出一条 TC，不做穷举
- **边界值分析**：所有数值型条件（阈值、比例、次数、时间窗口、金额上下限等）必须补充边界场景——**刚好等于边界、边界+1（略高于）、边界-1（略低于）** 三种取值都要有对应 TC。示例：某条件为"mmr > 阈值"，除了"明显大于"的主流程用例外，还要有"mmr恰好等于阈值"（不应触发，因为是`>`不是`>=`）和"mmr略低于阈值"的用例
- **判定表法**：当结果由多个条件组合决定时（如"条件A AND 条件B 同时满足才触发X"），先在设计阶段列出条件组合表（每个条件真/假的排列），核对每种组合是否都有对应 TC 或被有意省略并说明原因，避免只写了"全真"和"全假"两种漏掉"一真一假"的场景
- **状态转换测试**：涉及状态机的对象（账户状态、订单状态、审批流状态等），要覆盖每个状态到其他状态的合法转换，以及从非法源状态尝试转换（应被拒绝）的场景
- **正交实验法**：当条件组合数量过多、判定表法穷举不现实时，使用正交表挑选有代表性的组合子集，并在用例前置条件或模块说明中注明"采用正交法覆盖，未逐一穷举全部组合"
- **错误推测法**：结合经验补充文档未直接提及但容易出错的场景——空值/异常格式输入、并发操作/竞态、重复提交（幂等性）、超时、越权访问、网络/依赖服务失败、重试

### 分层覆盖思路
用例应覆盖以下四个层次，缺一层就在对应模块/分组里补齐：
- **单点验证**：单个接口/函数/配置项本身的输入输出、入参校验、错误码（对应功能逻辑各二级分组/Apollo/数据库）
- **链路验证**：跨系统的端到端数据流转（对应功能逻辑各二级分组）
- **配置驱动验证**：开关、阈值类配置在不同取值下的行为差异（对应Apollo/风控，结合等价类/边界值方法）
- **非功能验证**：并发、幂等、重试、超时、监控告警（穿插在功能逻辑/风控/Job中，对应错误推测法产出的场景）

### 正反场景配比要求
每个功能点必须同时具备：
- **正向场景**（happy path）：按预期输入走通主流程
- **反向场景**：非法/异常输入、越权、越界、依赖失败
- **边界场景**：由边界值分析产出，见上文

三者缺一不可，仅写正向场景视为覆盖不完整。

## 用例节点结构

### TC 用例（一级模块：功能逻辑/风控）
```
一级模块（彩虹色，如"功能逻辑"）
└── 前置条件：...（米黄）
└── 二级分组（按业务/端，如"现货"/"合约"/"管理后台"/"Web端"/"H5"/"搬砖套利"/"资金对冲"等策略型分组）
    └── 三级分组（按功能点，可选，如合约下的"开仓"/"强平"）
        └── TC-XX 用例名（浅灰加粗）
            ├── 额外前置：...（浅橙，可选）
            └── 测试步骤（浅蓝）
                ├── 步骤 1
                ├── 步骤 2
                └── 预期结果（浅绿）
                    ├── 分类子组（如「接口响应」「数据库」「站内信」）
                    │   ├── 验证项 1
                    │   └── 验证项 2
                    └── 单条验证项
```
二级/三级分组均用 `G()` 生成普通分组节点，不额外设颜色，跟随所在一级模块的彩虹底色。

### REF 引用节点（数据库/Apollo/Job）
```
DB-XX / AP-XX / JOB-XX 名称（浅灰加粗）
├── 关键字段（浅蓝）
│   ├── 字段名: 类型 说明（含索引/约束/枚举值）
│   └── ...
└── 验证要点（浅绿）
    ├── 业务逻辑要点 1
    └── ...
```

## 编号规则
编号前缀按**分组中文名的汉语拼音首字母**推导，不再用随意分配、需要死记硬背的单字母——看到前缀就能直接联想到分组名，新增分组时直接套算法生成，不用"自行约定"。

- **推导算法**：取分组中文名每个字的拼音首字母，大写拼接；2个字取2位，3个字及以上取前3位（超过3位可读性下降）。示例：
  - 现货 → xiànhuò → **XH**
  - 合约 → héyuē → **HY**
  - 风控 → fēngkòng → **FK**
  - 管理后台 → guǎnlǐhòutái → **GLH**（取前3位）
  - 回测 → huícè → **HC**
  - 搬砖套利 → bānzhuāntàolì → **BZT**（取前3位）
  - 资金对冲 → zījīnduìchōng → **ZJD**（取前3位）
  - 闪兑 → shǎnduì → **SD**
- **英文/专有名词分组不翻译，直接用其自身缩写**：Apollo → AP，Job → JOB，Web端/H5 保留原有习惯 → **W** / **H**（两个都是历史沿用的客户端类型缩写，非中文，不套拼音算法）
- **编号前缀按二级分组区分，不按一级模块区分**（一级模块"功能逻辑"内部会混合多个前缀）：
  - **现货**：TC-XH01、TC-XH02、...
  - **合约**：TC-HY01、TC-HY02、...
  - **管理后台**：TC-GLH01、TC-GLH02、...
  - **Web端**：TC-W01、TC-W02、...
  - **H5**：TC-H01、TC-H02、...
  - **风控**（独立一级模块）：TC-FK01、TC-FK02、...
  - **数据库**（独立一级模块）：DB-01、DB-02、...（REF节点，非TC，前缀固定不套拼音算法）
  - **Apollo**（独立一级模块）：AP-01、AP-02、...
  - **Job**（独立一级模块）：JOB-01、JOB-02、...
  - 量化交易相关分组（若启用，见"量化交易场景参考清单"）：回测→TC-HC、搬砖套利→TC-BZT、期现套利→TC-QX（qīxiàn）、资金对冲→TC-ZJD、闪兑→TC-SD
- **冲突处理**：同一份用例内若两个不同分组按算法推出相同前缀（概率低但可能），后出现的分组在末尾加数字区分（如 HY、HY2），并在模块说明里注明避免混淆
- 新增一个不在上述列表中的分组时，直接对分组中文名套用算法生成前缀，不需要临时决定或询问用户

## 颗粒度要求
- **禁止**将多条信息塞入同一个节点，每个独立信息点单独作为叶子节点 `L()`
- **层级不限**，以清晰易读为准，宁可多层也不堆砌
- 预期结果中有多类校验（接口/DB/MQ/站内信）时，**必须按分类分组**，不能平铺

## 覆盖完整性要求（生成前必须核对）
以下各项均为**举例**，括号中的具体名称（如某个配置项/消息码）只是示意格式，不是要求项目里真的存在这个字段：
- **接口**：技术文档所有接口（含 inner 接口）全部覆盖，不遗漏
- **错误码**：接口文档中列出的每一个错误码都必须有对应 TC
- **Apollo 开关**：所有布尔类配置开关（如某个功能的 `xxxOpen` 开关）必须有开/关两种场景用例，若启用了 Apollo 模块
- **站内信/通知**：文档中所有消息码/通知类型均需覆盖触发场景和内容验证，若业务涉及站内信
- **Job**：所有 Job（含复用的现有 Job）全部列入 Job 模块，若启用了 Job 模块
- **Redis Key**：所有 Key 的 TTL、幂等机制、并发场景均在功能逻辑对应分组中覆盖，若业务用到 Redis
- **MQ Topic**：所有新增 Topic 的生产-消费链路在功能逻辑对应分组中覆盖，若业务用到 MQ
- **DB 表**：技术文档所有新增表全部列入数据库模块，字段/索引/约束不遗漏
- **文档矛盾点**：发现文档前后矛盾时，在对应 TC 中标注（见下方"文档信息不全时的标注规范"）
- **方法论覆盖**：核对每个数值型条件是否已做边界值分析、每个多条件组合是否已过一遍判定表、是否补充了错误推测法产出的场景（见上方"用例设计方法"），不能仅覆盖文档字面提到的场景

## 文档信息不全时的标注规范
- 当需求/技术文档缺失细节（如具体阈值数值、接口协议、字段结构、错误码、命名空间/Key、矛盾点等），**禁止凭空捏造**，但必须显式标注，不能静默省略
- 标注方式：使用 `TODO(t)` 生成独立的红色加粗字体叶子节点（对应 `h.S_TODO`），**不要**再用纯文字前缀（如"【注意】""【待确认】"）夹在普通颜色的节点文字里——必须让这类信息在视觉上以红色区分，一眼可见
- 用法：
  - 若某条信息整体不确定（如某个阈值数值未给出），该叶子节点整体用 `TODO(...)` 而不是 `L(...)`
  - 若一条信息里既有已知的确定部分、又有不确定的部分，拆成两个同级节点：确定部分用 `L(...)`，不确定的说明单独用 `TODO(...)`，不要混在同一个节点文字里
  - 待确认内容里仍写明具体缺失什么、依据是什么（例如"文档未给出充值阀值具体数值，待与技术文档确认"），保留信息量，只是换成红色节点呈现
- 生成前的覆盖检查中识别出的"文档未覆盖/矛盾/含糊"点，最终都应体现为红色 `TODO` 节点，而不是被跳过

## Bitget 公开 API 知识库（条件触发）
